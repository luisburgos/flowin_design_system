How to Read the Flowin Design System Spec

A reader's tour of this repository for humans: the three-layer model, how a component contract is structured, how the tokens resolve, and how the spec becomes a technology-specific package.

Audience: humans (designers, engineers, reviewers) Repo: flowin_design_system (tech-agnostic spec) Companion: rationale-theme-first.html
Start here

This repo is the technology-agnostic source of truth for the Flowin design system. It asserts contracts and token values, never a specific rendering technique. AI agents transform it into technology-specific packages (Flutter first, others later). This guide orients a human reader; the normative material it points at lives in DESIGN.md, tokens/, and design/components/. For the long-form why behind the whole approach, read the companion theme-first rationale.

1The three-layer model

The spec is read top-down across three layers. Each layer answers a different question, and each has a different format and audience. They are not redundant: the tokens hold the values, the contracts hold the rules, and the docs hold the prose explanation.

Layer Where Format What it answers
1 · Tokens
the values		 tokens/ DTCG JSON The raw, machine-readable design values — color ramps, the spacing/radius/sizing scales, the type scale — and the semantic roles that alias them. Consumed by transforms, validated automatically.
2 · Contracts
the rules		 DESIGN.md + design/components/ Markdown The normative spine — the theme-first thesis, the theming model, the transformation contract — plus one fixed-template contract per component (intent, variants, sizes, token bindings).
3 · Docs
the explanation		 docs/ (you are here) HTML Human-facing prose: this usage guide and the long-form rationale. Reference reading, never a transform input.

The one idea under all three layers

The system is theme-first. Appearance is decided once, in the platform's own global theming mechanism — not recomputed inside wrapper widgets per call. Tokens feed a single theme; native widgets inherit the Flowin look; a thin component resolves only the two things a theme cannot know per call: which variant and which size. Everything in this repo serves that idea. The full argument is in the rationale; the normative statement is DESIGN.md §1.

2How to read a component contract

Every component is specified by one Markdown file under design/components/, following a fixed template (_TEMPLATE.md). The shape never varies, so once you can read one contract you can read all of them. The button contract is the worked reference.

Normative vs. illustrative — the key distinction

The most important thing to internalize: each section is either normative (a transform MUST satisfy it) or illustrative (it shows the reference implementation's shape but binds nothing). The template states this in its header, and each contract repeats it.

Normative — the binding contract

Intent, States, Token bindings, and Behavioral notes. These are the machine-targetable core: property × state → token reference. A conformant transform must reproduce them exactly.

Illustrative — not binding

Anatomy is the reference implementation's structure only. Where rendering is platform-dependent the contract says so and specifies intent, not the drawing. Don't treat anatomy as a requirement.

The fixed sections, in order

SectionStatusWhat it tells you
IntentNORMATIVEOne sentence: what the component is for, independent of how any platform renders it.
AnatomyILLUSTRATIVEThe reference structure. Not binding; flagged where platform-dependent.
VariantsNORMATIVEThe emphasis/purpose options a call site may choose (e.g. filled / tonal / outline / text / destructive).
SizesNORMATIVEThe footprint options and their notable dimensions (padding, min-height, paired icon size).
StatesNORMATIVEWhich interaction states apply (default · hover · pressed · focused · disabled).
Token bindingsNORMATIVEThe core table: each property × variant/state mapped to a {token.reference}. This is what a transform writes into the theme.
Behavioral notesNORMATIVEBehavior tokens can't express — gestures, async, helper APIs, disable-on-null-callback.
Theming directiveNORMATIVEThe split: what is styled globally (theme slot) vs. what the thin widget resolves per-call (variant, size, and any per-call role overlay).
Known gapsTRACKINGDocumented deviations from the reference and their planned fix (links the flowin_pm backlog).
Transform notesHINTSOptional per-technology hints: reference implementation name (e.g. FlowinButton), theme slots, the generic-primitive vs. domain/app-specific tag.

Reading the binding table

The Token bindings table is where a contract earns its keep. Each row reads property, the variant/state it applies to, and a {token.reference} in curly braces. The reference resolves against tokens/ — so the contract holds no literal hex or pixel values, only pointers into the token layer. For example, from the button contract: 

# Token bindings (normative)
| Property            | Variant / State | Token                          |
| shape corner radius | all             | {radius.400}                   |
| background          | filled, default | {color.primary}                |
| foreground          | filled, default | {color.onPrimary}              |
| background          | tonal, default  | {color.surfaceSecondary}       |
| content padding     | per size        | {space.*} (see Sizes table)   |

The accompanying Theming directive tells you which of these are installed once on the global theme (shape, base padding, base text style, per-variant color roles) versus resolved by the thin widget per call (variant selection, size dimensions, and the destructive error-role overlay). That global-vs-per-call split is the theme-first thesis made concrete for one component.

3How to read the tokens

The tokens live under tokens/ as DTCG JSON, in two tiers. The tokens/README.md is the authoritative index; this is the human walk-through.

Two tiers: primitive and semantic

TierFilesWhat it holds
Primitive
raw values		 primitive/color.tokens.json
primitive/dimension.tokens.json
primitive/typography.tokens.json
primitive/shadow.tokens.json		 The source palette and scales: neutral / error / warning / success 8-tier ramps (+ white/black); the spacing, corner-radius, border-width, and sizing (size.control, size.icon) scales; font families, weights, and composite type tokens; elevation shadows. Literal values, never consumed directly by components.
Semantic
role aliases		 semantic/color.light.tokens.json
semantic/color.dark.tokens.json
semantic/color.fixed.tokens.json		 The roles that components speak — a primary fill and its on-color, a surface and its on-color, surfaceSecondary/onSurfaceSecondary, borderSubtle, an error surface and its on-color. Each role is an alias pointing at a primitive. Light and dark define the per-mode role set; fixed holds mode-independent colors.

How aliases resolve

A semantic token does not carry a value — it carries a reference to a primitive, and the resolver follows it. A component binding (in a contract) points at a semantic role; the semantic role aliases a primitive ramp step; the primitive holds the literal. The chain is:

Resolution chain

component binding {color.primary}  →  semantic role color.primary  →  primitive ramp step {neutral.800}  →  literal #181818

Resolution is checked automatically: node tokens/validate.mjs walks every alias and fails on any dangling or circular reference. So if a contract names a role, you can trust that role resolves to a real primitive — the build won't let it dangle.

The neutralized role vocabulary

The semantic role keys are deliberately platform-neutral. They were initially aligned 1:1 with the reference implementation's native scheme (to keep the first transform easy to verify), and the most platform-specific names have since been neutralized to self-describing keys:

Neutral key (now)ReplacedMeaning
surfaceSecondary / onSurfaceSecondarya …Container familyThe tonal / secondary surface and the color legible on top of it.
borderSubtlean outline-variant keyThe subtle border / outline role.

Roles that were already neutral keep their names. Colour is never a bare value in the semantic tier — it is always a role paired with its on-color (the color legible on top of it). That pairing is what makes the contract platform-neutral, and it means a theme-level override of a role carries its on-color along. The rationale for this vocabulary is DESIGN.md §2.

Placeholder: primary / secondary / tertiary

The primary / secondary / tertiary roles are currently placeholder aliases to the neutral ramp — the brand has no chromatic accent yet. They exist as named slots awaiting a real palette. Note for readers: when you see a Flowin button rendered in grayscale, that is correct and intentional, not a bug. A transform must port them as the declared neutral aliases and must not fabricate a brand hue. Re-pointing them to chromatic values is tracked as a future revisit (see §5 and DESIGN.md §5). Note also that no primary / secondary / tertiary ramps live in primitive/ — those are semantic roles, not raw palette.

4How the spec becomes a tech-specific package

A transform takes the platform-agnostic tokens and contracts and binds them into one platform's global theming mechanism. The full, normative definition — including the mechanism mapping table and conformance rules — is DESIGN.md §3. This is the human summary.

Flutter is the named reference implementation (real and verified). A second column for CSS is shown in the spec as illustrative only — it demonstrates that the same token set maps onto a fundamentally different mechanism without changing the tokens. The mapping, in brief:

ConceptFlutter (reference)CSS (illustrative)
Semantic colorsBound onto ColorScheme roles; native widgets inherit from Theme.of(context).colorScheme.Custom properties on :root (--color-primary, …).
TypographyBound onto TextTheme slots.Custom properties + utility classes.
Spacing / radius / non-nativeCarried on a ThemeExtension, read via a typed context accessor.Custom properties under :root.
Component appearanceBound onto per-component theme slots (filledButtonTheme, …); the native widget renders Flowin by default.Component classes (.flw-button--filled, …) resolving the custom properties.

The acceptance test for a transform

A transform is conformant only if every token binding is globally overridable, not per-instance: changing it once on the global theme must change every consumer. The concrete acceptance test is theme-overridability — for any documented binding, it must be possible to override it purely through the theme, render the component unchanged, and observe the override. The reference implementation proves this for the button: a test overrides the filled-button shape on the theme, pumps the button unchanged, and reads the themed radius off the rendered surface. (See DESIGN.md §3 → Conformance rules.)

What a transform must NOT do

Don't apply per-instance hardcoded styling; don't invent values for documented gaps (leave a placeholder/alias as declared — no fabricated brand hue, no fabricated dark on-color); don't collapse variants or sizes; and don't rename a token reference without updating its bindings in the same change. The full "Do not" list is DESIGN.md §3.

5Where planned work lives

This repo holds the spec as it stands. Anything planned, deferred, or known-missing lives in the program-management backlog, not scattered through the spec:

  • Program planning & the backlog: flowin_pm — milestones, scoped work items, and the running list of intentionally-trimmed or legacy-only capabilities.
  • Declared gaps (so transforms don't invent values): DESIGN.md §5 enumerates them — the chromatic brand accent for primary/secondary/tertiary, the missing dark-mode onSurfaceBright / onSurfaceBrightVariant on-colors, the primary/secondary 400-step divergence, and legacy-only component capabilities. Each is tracked in flowin_pm.
  • Per-component planned fixes: each contract's Known gaps / planned fix section records its own deviations and links the backlog.
