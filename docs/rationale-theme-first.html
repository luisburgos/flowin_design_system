Flowin Design: Legacy FD* Widgets vs. a Modern Theme-First Flutter Architecture

A component-by-component review of the legacy flowin_design package against the rebuilt, theme-first flutter_flowin package — with a migration verdict for every widget the legacy package ships.

Legacy: flowin_design (lib/src/foundations, lib/src/components) Modern: flutter_flowin (lib/src/theme, lib/src/widgets) Scope: foundations + 20 component files
Where this lives now

This document is the long-form "why theme-first" rationale for the Flowin design system. It originated as an engineering analysis in the Flutter reference implementation (flutter_flowin) and now lives in the technology-agnostic spec repo (flowin_design_system) as foundational rationale — the narrative behind the normative thesis in DESIGN.md §1. It is preserved verbatim: the comparison is grounded in Flutter source, so ThemeData, ColorScheme, and the FD* / Flowin* class names below are the reference implementation's vocabulary, illustrating the platform-neutral argument the spec generalizes. For a reader's tour of the spec itself — the three-layer model, how to read a contract, how to read the tokens — see usage-guide.html.

1Executive summary & thesis

The legacy flowin_design package gets the hard part right and the easy part wrong. Its design tokens are excellent: a complete, well-named foundation layer covering color, spacing, radius, borders, shadow, typography (Inter baseline + bundled Supreme brand font), icon sizing with paired stroke weights, and a lucide-backed icon map. That layer is worth keeping verbatim.

The problem is everything built on top of it. The component layer is a set of over-engineered, closed FD* widget wrappers that bypass Material's component themes and recompute styling per instance, inside each widget's build() method. FDButton calls getFDButtonVariantColors() and getVariantSizePadding() on every build; FdChip resolves its background and border from the ColorScheme by hand; FDDivider reaches for colorScheme.outlineVariant directly. The shared ThemeData the package ships configures only colorScheme, textTheme, and scaffoldBackgroundColor — it defines zero component ThemeData. So the styling has nowhere to live but the widgets, and the widgets become the only supported way to render a styled button, chip, or divider.

Thesis

Port the tokens 1:1, then feed them into a single theme builder that produces ThemeData with full component themes (FilledButtonThemeData, ChipThemeData, TabBarThemeData, DividerThemeData, InputDecorationTheme, CardThemeData, BottomSheetThemeData, IconButtonThemeData, …) plus a FlowinTokens ThemeExtension for the non-Material tokens (spacing scale, semantic colors, brand text styles, base shadow, default icon size), accessed via context.flowinTokens. Native widgets — and the thin Flowin widgets that compose them — are then styled entirely by the theme, with no per-instance styling. Custom widgets survive only where Flutter has no equivalent.

The modern package already proves this for FlowinButton. The button hardcodes no shape and no corner radius; those come from filledButtonTheme on the theme. The widget test test/src/widgets/flowin_button_test.dart asserts exactly this: it overrides the filled-button shape in the theme, pumps a FlowinButton.filled, then reads the resolved shape off the rendered Material and expects it to reflect the theme's radius — "corner radius comes from the theme, not the widget (theme-only styling)." The button only resolves the two concerns the theme genuinely cannot know per call: which variant and which size.

3The theme-assembly gap — the core problem

Everything in section 1 traces back to one file. Legacy FlowinDesignThemes._themeData (in lib/src/foundations/themes.dart) builds ThemeData from the scheme and text theme and stops there: 

// legacy — lib/src/foundations/themes.dart
static ThemeData _themeData(ColorScheme colorScheme, Brightness brightness) {
  var baseTheme = ThemeData(brightness: brightness);
  baseTheme = baseTheme.copyWith(textTheme: FlowinTypefaces.baseline());

  return ThemeData(
    useMaterial3: true,
    colorScheme: colorScheme,
    scaffoldBackgroundColor: colorScheme.surface,
    textTheme: baseTheme.textTheme,
    // ← no filledButtonTheme, chipTheme, tabBarTheme,
    //    dividerTheme, inputDecorationTheme, cardTheme,
    //    bottomSheetTheme, iconButtonTheme … nothing.
  );
}

With no component themes defined, component styling has nowhere to live but inside the widgets — so every FD* wrapper recomputes its own look on each build. Compare the two approaches for a button:

Legacy — styling computed inside the widget

// FDButton.build — runs every rebuild
final colors = getFDButtonVariantColors(
  context, variant: variant,
);

final style = styleFrom(
  context,
  variant: variant,
  size: size,
  foregroundColor: colors.foregroundColor,
  backgroundColor: colors.backgroundColor,
);

return Container(
  padding: EdgeInsets.symmetric(
    vertical: size.padding,
  ),
  child: FilledButton(
    onPressed: onPressed,
    style: style,          // per-instance
    child: effectiveChild,
  ),
);

// styleFrom hardcodes padding, minimumSize,
// iconSize, fg/bg, textStyle — all per call.

Modern — styling lives in the theme

// in the theme builder, once:
filledButtonTheme: FilledButtonThemeData(
  style: FilledButton.styleFrom(
    padding: buttonPadding,
    shape: buttonShape,     // radius400
    textStyle: buttonTextStyle,
  ),
),

// FlowinButton.build — resolves ONLY
// per-call variant + size:
final sizeStyle = ButtonStyle(
  padding: WidgetStatePropertyAll(size.padding),
  minimumSize: WidgetStatePropertyAll(
    Size(0, size.minHeight),
  ),
  iconSize: WidgetStatePropertyAll(
    size.iconSize.value,
  ),
);

return FilledButton(           // shape/radius
  onPressed: onPressed,        // from theme
  style: sizeStyle,
  child: content,
);
Why this matters

Because styling is trapped in the wrappers, a consumer can't get a Flowin-styled button by using a native FilledButton — they must use FDButton. The design system becomes a closed widget catalog instead of a theme. Pushing the same decisions into component ThemeData inverts this: native widgets render correctly by default, and the thin Flowin widgets exist purely to expose ergonomic variant/size APIs.

Pattern across the table

Wherever the legacy widget only repackaged a native widget with styling (FDButton, FDIconButton, FdChip, FDTabs/FDTabItem, FDDivider, FDTextField) → REPLACE: the styling moves to a component theme and the wrapper either disappears or becomes a thin variant/size shim. Wherever it contributed real logic or layout/UX Flutter doesn't ship (FdChipGroup, FDChipGroupViewPager, FDInputField, FDColorPickerField, action-sheet header/footer, FDCard, FDColorRadialButton) → KEEP (refactored to consume the theme).

5Recommended modern architecture

This is the design already realized in flutter_flowin. The data flows in one direction: raw tokens → theme builder → extension → context accessors → thin widgets.

  1. foundations/ — raw tokens. The legacy foundation classes, ported 1:1 (FlowinDesignColors, FlowinDesignSpace, FlowinDesignRadius, FlowinDesignBorders, FlowinDesignShadows, FlowinDesignIconSize, the Inter/Supreme text tokens, the FDIcons map, and the FlowinDesignSchemes light/dark ColorSchemes).
  2. FlowinTheme — the single theme builder. Produces light and dark ThemeData with full component themes: filledButtonTheme, outlinedButtonTheme, textButtonTheme, iconButtonTheme, dividerTheme, chipTheme, tabBarTheme, cardTheme, inputDecorationTheme, and bottomSheetTheme. Everything Material already models lives here.
  3. FlowinTokens — the ThemeExtension. Home for tokens with no Material slot: the FlowinSpacing scale, FlowinSemanticColors (success / warning / info + on-colors, with light/dark variants), the base shadow, and the defaultIconSize. Implements copyWith and lerp so it animates with the rest of the theme.
  4. context.flowinTokens — typed accessors. The FlowinThemeBuildContext extension exposes theme, colorScheme, textTheme, flowinTokens, spacing, and semanticColors off any BuildContext.
  5. widgets/ — thin widgets. FlowinButton is the reference: it composes native buttons and reads shape/radius/text style from the theme, resolving only per-call variant + size. Custom widgets (card, color swatch, input-field shell, action-sheet parts) live here too, consuming the theme rather than hardcoding styling.

Verified

The token values are a true 1:1 port (the color definitions compare byte-for-byte identical to the legacy file), the component themes are populated, and the flowin_button_test.dart "theme-only styling" test passes — confirming the architecture works end-to-end for the reference component.

6Migration implications

Because the new package keeps the legacy class names for the foundation layer — FlowinDesignColors, FlowinDesignSpace, FlowinDesignRadius, FlowinDesignBorders, FlowinDesignShadows, FlowinDesignIconSize, FDIcons, FlowinDesignSchemes, and the text tokens — any consuming app that references tokens directly continues to compile essentially unchanged. The token surface is a stable contract.

The widget-level migration is then largely mechanical, in two buckets:

  • REPLACE call sites swap an FD* wrapper for the native widget or the thin Flowin widget: FDButton(…) → FlowinButton(…) (or FilledButton), FDDivider() → Divider(), FdChip(…) → Chip(…), FDTextField(…) → TextField(…). The theme supplies the styling these used to compute, so the visual result is unchanged.
  • KEEP call sites (chip group/pager, input-field shell, color picker, action-sheet parts, card, radial swatch) keep their widget names; only their internals change to read from the theme. Call sites need little or no edit.
Bottom line

Adopting the app to flutter_flowin is a find-and-replace on the FD* widget layer over a stable token layer — not a rewrite. The one-time investment is concentrated in the theme builder (already done) and in refactoring the handful of KEEP widgets to consume the theme rather than recompute styling.
